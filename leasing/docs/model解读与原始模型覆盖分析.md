# 融资租赁本体模型解读与原始模型覆盖分析

本文解读当前 `leasing/model.yaml`，并与 `融资租赁数据模型.puml` 及其引用的
`_实体定义.iuml` 进行概念层对照。

这里的“覆盖”不是把原始数据表和字段逐个搬到 YAML，而是判断一个业务概念是否仍能被
识别、关联和追溯。为避免把“可表达”误解为“已实现”，本文分开说明三个层次：

- 语义模型：`model.yaml` 定义了哪些对象、关系和属性。
- 执行模型：哪些业务行为已经定义为 Action，可通过前端或 Agent 执行。
- 数据示例：Seed 图中已经有哪些具体业务事实和追溯路径。

## 1. 模型的核心思路

UOM 核心本体只定义两种图元素：

```text
Object    可独立识别、保存和追溯的业务事实
Relation  两个 Object 之间有方向、可带属性的业务联系
```

`leasing/model.yaml` 在此之上定义融资租赁领域语义。当前共有：

| 模型元素 | 数量 | 职责 |
| --- | ---: | --- |
| Object 类型 | 21 | 表达主体、授信、合同、资金、核算和审批事实 |
| Relation 类型 | 5 | 以少量稳定关系和 `role` 表达具体联系 |
| Action | 13 | 把用户业务意图编译为可预览、可确认的 ChangeSet |
| 确定性函数 | 4 | 概览、合同追溯、查找未核销收款和一致性审计 |

模型没有按原始资料中的数据表和外键逐表复刻，而是保留对经营判断重要的事实和业务路径：

```text
客户 -> 授信 -> 额度流水
  |       |
  +-----> 项目方案 -> 审批 -> 合同 -> 放款
                                      |
                                      +-> 租金计划版本 -> 应收 -> 罚息

客户 -> 收款 -> 核销明细 -> 应收 / 罚息

合同 -> 变更 / 标的物 / 担保 / 结清 / 凭证
```

这个模型主要回答：

- 这笔融资业务由谁参与，依据什么授信、方案和审批形成？
- 合同产生了哪些放款、租金计划、应收和罚息？
- 到账资金核销了哪些应收或罚息，金额是否守恒？
- 合同发生了哪些变更、担保、结清、开票和会计处理？

## 2. 当前 21 个对象类型

### 2.1 主体、授信和方案

| 对象 | 含义 |
| --- | --- |
| `party` | 出租方、资金方、业务部、风险部或服务机构等经营主体。 |
| `customer` | 承租方、买方、卖方或保证人等客户侧主体。 |
| `credit` | 客户可使用的授信额度总量及其有效期和状态。 |
| `credit_entry` | 额度预占、占用、释放、冲销或预占转占用的一次变动事实。 |
| `lease_plan` | 合同签订前对融资金额、期限和租金方案的业务申请。 |

额度的“已预占”和“已使用”不是反复覆盖的录入字段，而是由 `credit_entry` 按变动类型
汇总得出。这样可以追溯额度何时、因何被预占或正式使用。

### 2.2 合同和履约

| 对象 | 含义 |
| --- | --- |
| `contract` | 约定出租、承租、放款、租金和标的物责任的核心合同事实。 |
| `contract_participation` | 某个主体以某种角色参与合同的事实，可保存生效期间。 |
| `loan` | 合同项下一次实际资金投放。 |
| `schedule_version` | 某一版租金计算和收款计划；新版本不覆盖旧版本。 |
| `change_order` | 展期、提前还款、利率调整或租金重排等合同变更事实。 |

`schedule_version` 通过 `supersedes` 指向被替代的旧版本。已由旧版本生成的应收、收款和
核销仍保留原始来源，不会因租金计划调整而被改写。

### 2.3 应收、收款和结算

| 对象 | 含义 |
| --- | --- |
| `receivable` | 一笔具体应收，可以是租金、费用或其他应收。 |
| `payment` | 一笔实际到账资金；到账不等于已经归属到某笔应收。 |
| `allocation` | 收款分配给应收或罚息的独立核销事实，包含金额、日期和顺序。 |
| `penalty` | 应收逾期后计提的一笔罚息事实。 |
| `settlement` | 合同最终结算或部分提前结清事实。 |

`allocation` 是资金追溯的关键中间事实：

```text
payment ->derives-> allocation ->references-> receivable / penalty
```

因为核销金额属于“这次分配”，它不应只是一条无属性的 `payment -> receivable` 关系。
独立的 `allocation` 既能表达一笔收款核销多笔应收，也能表达一笔应收被多次收款分次核销。

### 2.4 标的、担保、账务和审批

| 对象 | 含义 |
| --- | --- |
| `subject_matter` | 设备、车辆或受让应收账款等租赁标的及其价值事实。 |
| `guarantee` | 保证人或担保物为合同提供担保的方式、金额和顺位事实。 |
| `invoice` | 由应收或结算事实产生的开票结果。 |
| `voucher` | 业务事实投影形成的会计凭证头。 |
| `voucher_line` | 凭证下的借方或贷方分录。 |
| `approval` | 针对一个业务对象发起的一次审批决策事实。 |

审批没有拆成流程、节点和任务等多个本体对象。本次审批采用的流程快照、处理历史和
最终结果分别保存在 `approval.details.process/history/result` 中。被审批对象通过 `references`
关系连接，提交主体和决策主体通过 `associates` 关系连接。

## 3. 五种稳定关系

| 关系 | 当前语义 | 例子 |
| --- | --- | --- |
| `contains` | 整体包含组成或明细事实。 | `voucher -> voucher_line`、`contract -> contract_participation` |
| `references` | 一个事实引用另一对象作为来源、依据或业务对象。 | `approval -> lease_plan`、`allocation -> receivable` |
| `associates` | 两个独立对象存在业务联系，具体含义由 `role` 说明。 | `payment -> customer`、`contract -> subject_matter` |
| `derives` | 来源业务事实经过处理产生结果事实。 | `contract -> loan`、`schedule_version -> receivable` |
| `supersedes` | 新版本替代旧版本，旧事实仍保留。 | `schedule:v2 -> schedule:v1` |

原始 PUML 通过 65 条具体连线表达包含、聚合和业务引用。当前模型不为每条连线新建一个
关系类型，而是用上述五种关系加 `role` 表达具体语义。这是关系词汇的有意收敛，不是把
原始 65 条关系机械地缩减成 5 条。

关系与属性的边界是：

- “客户 ID”“合同 ID”“来源单据 ID”等外键语义改由关系表达，不再作为普通属性重复保存。
- 对象本身的金额、日期、状态、分类和版本等事实保留为属性。
- 关系自身的角色、顺序、状态和发生日期可保存在关系属性中。
- 可沿图路径无歧义得到的关系不重复建边。例如应收可由租金计划追溯到合同，不必再保存平行的合同外键。

## 4. 业务操作模型

对象和关系说明“业务世界中有什么”，Action 说明“用户可以做什么”。当前 13 个 Action 中，
11 个声明了共 18 条 `requires` 前置条件；登记客户和发起审批没有前置业务状态要求。Action 清单是：

| Action | 业务含义 | 显式业务对象 |
| --- | --- | --- |
| `register_customer` | 登记客户 | 无，该操作创建新客户 |
| `grant_credit` | 为客户授予额度 | `customer_id` |
| `create_lease_plan` | 为客户创建方案并预占授信 | `applicant_id` |
| `start_approval` | 针对业务对象发起审批 | `reviewed_object` |
| `record_approval_decision` | 记录阶段或最终审批决定 | `approval_id` |
| `sign_contract` | 将已审批方案落地为合同，建立参与事实并转换额度 | `lease_plan_id` |
| `record_loan` | 登记合同项下放款 | `contract_id` |
| `create_schedule_version` | 为合同建立租金计划版本 | `contract_id` |
| `create_receivable` | 根据租金计划版本生成应收 | `schedule_version_id` |
| `record_payment` | 登记客户到账资金，可选记录意向合同 | `payer_id` |
| `allocate_payment` | 将收款核销到应收或罚息 | `payment_id` |
| `settle_contract` | 记录合同结清事实 | `contract_id` |
| `issue_voucher` | 从合同生成平衡的借贷凭证 | `accounting_source` |

当前有 `subject_matter`、`guarantee`、`penalty`、`change_order` 和 `invoice` 等对象类型，但尚未为它们定义
专门 Action。因此，这些概念已经可以被模型和图数据表达，但还不能都通过领域化业务表单完成。

Action 的 Effects 使用三个与领域无关的最小写操作：

| Effect | 含义 | 当前用途 |
| --- | --- | --- |
| `create_object` | 创建一个业务事实对象 | 客户、授信、方案、合同、资金和凭证等新事实 |
| `create_relation` | 在两个对象之间建立有角色的业务联系 | 方案引用客户、合同派生放款、核销指向应收等 |
| `update_object` | 更新已有对象的属性 | 推进审批、方案、合同、计划、收款和应收等业务状态 |

`model.yaml` 只声明操作的输入、前置条件和基础 Effects。融资租赁领域处理器只保留确实属于领域的补充逻辑：
审批决定追加历史、区分阶段与最终决定，以及在预览阶段执行资金一致性审计。

### 4.1 用 `requires` 表达操作依赖图

一笔融资租赁业务不是唯一的线性工作流：放款和租金计划都可以依赖合同，收款又可能早于应收到账。
因此 `model.yaml` 不使用“步骤 1、步骤 2”规定唯一顺序，而是为 Action 声明 `requires` 前置条件。
所有 Action 的前置条件合起来形成一张操作依赖图。

当前 DSL 支持两种最小条件：

| 条件 | 含义 | 例子 |
| --- | --- | --- |
| `object_status` | 指定输入对象必须处于允许状态 | 只有 `active` 合同可登记放款；只有 `pending` 审批可记录决定 |
| `related_object` | 图中必须存在符合类型、关系、`role` 和属性的关联对象 | 方案必须有已通过审批；签约授信必须是方案预占的授信 |

例如签约前的审批条件直接定义在 `sign_contract` 下：

```yaml
requires:
  - related_object:
      from_type: approval
      to: $input.lease_plan_id
      relation: references
      role: reviewed_object
      properties: {status: approved}
      message: 签订合同前，项目方案必须存在已通过的审批。
```

运行时在三个时点评估这些条件：

- 读取对象可用操作时，返回 `executable` 和 `blocked_reasons`；前端锁定受阻操作并显示原因。
- 预览 Action 时，用完整表单输入校验所有条件，不满足就不生成 ChangeSet 确认令牌。
- 用户确认提交时再次校验，防止预览后对象状态或关系已发生变化。

当前 18 条前置条件按操作归纳如下：

| Action | 前置条件 |
| --- | --- |
| `record_approval_decision` | 审批必须处于 `pending`。 |
| `grant_credit` | 客户必须处于 `active`。 |
| `create_lease_plan` | 客户和授信必须为 `active`，且授信必须属于该客户。 |
| `sign_contract` | 方案必须有已通过审批且状态为 `approved`；授信必须有效、属于该方案预占的授信；承租方必须是方案申请客户。 |
| `record_loan` | 合同必须处于 `active`。 |
| `create_schedule_version` | 合同必须处于 `active`。 |
| `create_receivable` | 租金计划版本必须处于 `active`。 |
| `record_payment` | 付款客户必须处于 `active`。 |
| `allocate_payment` | 收款必须为 `unallocated` 或 `partial`，核销目标必须为 `open` 或 `partial`。 |
| `settle_contract` | 合同必须处于 `active`。 |
| `issue_voucher` | 合同必须为 `active` 或 `settled`。 |

这些条件构成的是偏序依赖，而不是一条强制的流水线。例如合同生效后，放款和建立租金计划可以分别进行；
登记收款只要求付款客户有效，不强制等待应收生成。到账后的最终业务归属由后续核销路径确定。

### 4.2 业务对象不再隐含于 UI 上下文

所有依赖已有对象的 Action，都把该对象定义为必填输入。例如，发起审批不再假定“当前页面
选中的对象就是被审批对象”，而是显式定义：

```yaml
context_input: reviewed_object
inputs:
  reviewed_object:
    name: 被审批对象
    object_types: [lease_plan, contract, loan, change_order, allocation, settlement]
    required: true
```

Action Effect 也引用 `$input.reviewed_object`，而不是 `$context`。这样：

- Agent 不依赖对象详情页，也能明确指定本次操作的业务对象。
- 前端从对象详情页打开 Action 时，仍可以按 `context_input` 自动预填当前对象。
- UI 上下文和显式对象输入同时存在但不一致时，运行时会拒绝执行，避免把业务事实记到错误对象上。
- `context_input` 只是 Action 与 UI 之间的预填协议，不是新的本体概念，也不写入业务图。

### 4.3 审批闭环

当前审批过程是：

```text
发起审批
  -> 创建 approval
  -> references(reviewed_object) -> 被审批对象
  -> associates(submitted_by) -> 提交主体
  -> 多次记录阶段决定
  -> 记录最终决定
  -> 审批通过后允许方案签约
```

每次决定都追加到 `approval.details.history`，并通过 `associates(decided_by)` 连接决策主体。
非最终决定不会把审批状态提前改为通过或拒绝；只有 `is_final: true` 才更新
`approval.details.result` 和最终状态。`sign_contract.requires` 会查找指向当前方案的已通过审批，
没有通过时拒绝签约。该约束已从 Leasing Python 特例中移除，由 `model.yaml` 单一声明。

这里的职责边界是：通用 Action 运行时负责执行 `update_object`，Leasing 处理器负责把一次决定整理成
`details.history` 和 `details.result`。因此，审批历史属于领域语义，而对象更新能力仍属于 UOM 通用执行协议。

当前审批仍是 MVP 实现，已知边界是：

- `process` 仍是由用户提供的 JSON 快照，尚未有模型内审批流程模板。
- 运行时尚未校验决策主体是否属于当前流程步骤，也没有强制步骤顺序、会签人数和最终步骤。
- `decision`、审批类型和流程角色尚未收敛为受控枚举。
- 一个 `start_approval` 当前只接受一个被审批对象，尚未实现原始模型的批量审批和逐单据执行结果。

### 4.4 操作结果闭环

对象状态属于业务操作结果，不再作为普通表单输入让用户任意选择。当前主要状态迁移是：

```text
项目方案：draft -> pending_approval -> approved / rejected -> contracted
收款：    unallocated -> partial -> allocated
应收/罚息：open -> partial -> settled
合同：    active -> settled
计划版本：active -> inactive（由新版本 supersedes，或合同结清）
```

这些迁移同时产生必要的业务事实：

- 方案审批被拒时，保留原预占流水，并新增 `release` 流水释放额度。
- 签约金额必须与方案金额一致；签约后方案变为 `contracted`，同一方案不能再次签约。
- 合同已有生效租金计划时，新版本必须显式选择 `supersedes_id`；旧版本失效但不删除。
- 核销根据历史核销加本次金额计算双方状态，全额时分别变为 `allocated` 和 `settled`。
- 最终结清前，合同路径上的应收和罚息必须全部为 `settled`；结清后关闭合同、参与事实和生效计划，
  并新增 `reverse_occupy` 流水释放该合同实际占用的授信。

核销比例、合同债权范围和授信待释放金额需要读取当前图并做确定性计算，因此由
`LeasingActionService` 丰富 ChangeSet；对象更新和事务提交仍由 UOM 通用运行时完成。预览后的图还会再次执行
资金一致性审计，状态与累计金额不一致同样不能提交。

## 5. Seed 数据示例的读法

当前 Seed 是用于验证模型语义的多案例数据集，共有 90 个对象和 128 条关系，覆盖全部
21 个对象类型和 5 个关系类型。它不再把所有概念勉强塞进一笔业务，而是并列保留：

- 济南智能产线：方案审批通过后签约，合同发生利率调整，旧租金版本被新版本替代，并存在部分核销和待认领收款。
- 青岛医疗设备：方案处于审批中，额度保持预占，尚不能签约。
- 潍坊物流车辆：方案审批被拒，预占额度通过 `release` 流水完整释放。
- 烟台海工装备：两次放款、多期应收、两笔收款交叉核销，其中一笔收款同时核销租金和罚息。
- 淄博节能窑炉：合同履约结束并结清，已用授信通过反向流水释放，尾款、核销、结清事实和会计凭证仍可沿图追溯。
- 临沂停用客户：用于验证依赖有效客户的授信、方案和收款操作会被前置条件阻止。

其中济南案例可以读成：

```text
济南智造有限公司
  <-references- 智能产线融资租赁方案
综合授信额度
  ->contains-> 方案额度预占 / 合同额度正式占用
智能产线融资租赁方案
  ->derives-> 融资租赁合同
融资租赁合同
  ->contains-> 承租方 / 出租方参与事实
  ->derives-> 首笔放款
  ->derives-> 租金计划 V1
利率调整变更单
  ->derives-> 租金计划 V2 ->supersedes-> 租金计划 V1
租金计划 V1
  ->derives-> 第 1 期租金 / 第 2 期租金
第 2 期租金
  ->derives-> 逾期罚息
客户
  <-associates- 收款 PAY-001
收款 PAY-001
  ->derives-> 两笔核销明细
两笔核销明细
  ->references-> 第 1 期租金 / 第 2 期租金
合同
  ->derives-> 部分提前结清单
应收
  ->derives-> 发票
会计凭证
  ->contains-> 借方分录 / 贷方分录
方案审批
  ->references(reviewed_object)-> 智能产线融资租赁方案
  ->associates(submitted_by / decided_by)-> 业务部 / 风险部 / 出租方
变更审批
  ->references(reviewed_object)-> 利率调整变更单
```

Seed 在写入前同时执行结构校验和资金一致性审计。当前样本明确验证：方案审批对象与签约条件一致；
授信预占、转占用和释放后的余额守恒；一笔收款可核销多个目标、一笔应收可由多笔收款核销；
罚息可以作为独立核销目标；每张凭证借贷平衡。它仍不等于所有对象都已有专门 Action，也不等于
一笔数据已完成原始 35 实体模型的全字段填充。

## 6. 确定性函数和业务约束

LLM 负责理解意图和组织解释，金额守恒和图追溯交给确定性函数。当前四个领域函数是：

| 函数 | 用途 |
| --- | --- |
| `get_finance_overview` | 统计对象、关系和各类金额，并返回一致性审计结果。 |
| `get_contract_trace` | 从合同出发，按深度追溯关联对象和关系。 |
| `find_unallocated_payments` | 查找尚未产生任何 `allocation` 的收款。 |
| `audit_finance_consistency` | 审计核销、授信流水和凭证借贷守恒。 |

`find_unallocated_payments` 当前识别的是“完全未核销”收款；一笔收款只要已经有一条核销明细，
就不会出现在返回列表中。部分核销后的未分配余额可以由核销汇总计算，但尚未由该函数单独返回。

当前确定性约束包括：

- 每条核销必须恰好来自一笔收款，并恰好指向一笔应收或罚息。
- 同一收款的累计核销不能超过到账金额。
- 同一应收或罚息的累计核销不能超过业务金额，并且两端币种必须一致。
- 授信预占和已用金额由额度流水汇总，不能为负数，总额不能超过授信。
- 每张凭证的借方和贷方合计必须平衡，分录方向必须是 `debit` 或 `credit`。

Action 会先编译为包含对象创建、对象更新和关系创建的 ChangeSet，再投影到当前图上执行审计。审计失败时不会生成
提交令牌；通过审计的变更仍需经过预览和用户确认才会以事务写入 SQLite。

## 7. 与原始 35 个实体的对照

`_实体定义.iuml` 定义了 35 个实体。当前模型定义 21 个独立 Object 类型，但不是简单的
21 对 35 删减：`subject_matter` 吸收了两类标的物子类的专属信息，`approval` 也用内部历史和
参与主体关系概括了审批明细的一部分语义。

### 7.1 已直接或抽象覆盖的 24 个概念

| 原始实体 | 当前模型 | 处理方式 |
| --- | --- | --- |
| 客户 | `customer` | 直接覆盖 |
| 经营主体/出租方 | `party` | 抽象为更通用的经营主体 |
| 授信额度 | `credit` | 直接覆盖 |
| 额度占用流水 | `credit_entry` | 统一表达预占、占用、释放、冲销和预占转占用 |
| 项目方案 | `lease_plan` | 用更明确的领域名称覆盖 |
| 主合同 | `contract` | 直接覆盖 |
| 合同参与方 | `contract_participation` | 将角色与生效期间提升为可追溯事实 |
| 放款 | `loan` | 直接覆盖 |
| 租金表版本 | `schedule_version` | 用计划版本和 `supersedes` 表达版本演进 |
| 标的物主表 | `subject_matter` | 直接覆盖 |
| 标的物—租赁物 | `subject_matter.details` | 租赁物专属信息暂存 `details`，未独立成类型 |
| 标的物—受让应收账款 | `subject_matter.details` | 受让应收账款专属信息暂存 `details` |
| 担保关系 | `guarantee` | 作为带金额、方式和顺位的独立事实 |
| 合同变更单 | `change_order` | 直接覆盖 |
| 应收计划明细 | `receivable` | 直接覆盖 |
| 逾期罚息计提 | `penalty` | 直接覆盖 |
| 收款单 | `payment` | 直接覆盖 |
| 核销明细 | `allocation` | 作为独立资金分配事实 |
| 结清单 | `settlement` | 直接覆盖 |
| 开票信息 | `invoice` | 直接覆盖发票头事实 |
| 凭证 | `voucher` | 直接覆盖 |
| 凭证分录 | `voucher_line` | 直接覆盖 |
| 审批申请单 | `approval` | 直接覆盖，流程快照、历史和结果收进 `details` |
| 审批单据明细 | `approval.details.history` 与关系 | 覆盖单对象审批的决策追溯，尚未覆盖批量单据执行状态 |

按“概念是否还能表达”的宽口径，当前覆盖约 `24 / 35`，即 69%。其中标的物子类和审批明细只是
抽象覆盖，并非原字段和原行为完全等价。按独立 Object 类型数量计算则是 `21 / 35`，即 60%。

### 7.2 尚未作为独立对象覆盖的 11 个概念

| 原始实体 | 当前状态 | 主要影响 |
| --- | --- | --- |
| 从合同 `sub_contract` | 未建模 | 无法独立追踪主合同下的从合同及其金额、类型和标的物来源 |
| 保证金计划 `deposit_plan` | 未建模 | 方案、合同或放款约定的保证金无法结构化追踪 |
| 费用计划 `fee_plan` | 未建模 | 手续费等费用的计划、内扣和税率无法独立追踪 |
| 租金表明细 `rent_line` | 未建模 | 租金版本没有独立的本金、利息、计息区间和剩余本金明细 |
| 担保物 `collateral` | 未建模 | 无法独立表达担保物评估价值、权证和状态 |

| 催收记录 `collection` | 未建模 | 无法保存催收方式、结果、承诺还款日和后续跟进 |

## 8. 关系、属性和执行覆盖的边界

### 8.1 已能直接或沿图表达的关系

- 客户获得授信、客户申报方案：通过 `references` 表达。
- 授信产生额度流水：通过 `contains` 表达。
- 方案落地为合同：通过 `derives` 表达。
- 合同参与方：通过 `contract -> contains -> contract_participation -> references -> party/customer` 表达。
- 合同产生放款和租金计划，租金计划产生应收，应收产生罚息：通过 `derives` 表达。
- 收款与付款人、合同与标的物/担保、担保与保证人：通过 `associates` 表达。
- 收款与核销、核销与应收/罚息：通过 `derives` + `references` 表达。
- 凭证与分录：通过 `contains` 表达。
- 审批与被审批对象、提交主体和决策主体：通过 `references` + `associates` 表达。

原始模型中有些直接外键被当前模型改为了业务路径。例如应收由租金计划派生，租金计划又由合同派生，
因此可沿图追溯到合同，不再重复保存应收的合同 ID。收款与合同的关系只表示到账时的意向归属，
最终资金归属仍由 `payment -> allocation -> receivable/penalty` 路径决定。

### 8.2 当前确实缺少的关系能力

由于对应对象尚未建立，以下业务路径目前无法独立表达：

- 合同与从合同、从合同与标的物来源合同；
- 方案/合同/放款与保证金计划、费用计划；
- 租金版本与本金、利息、计息区间明细；
- 标的物与担保物、担保物与担保关系；
- 合同与风险分类、催收记录；
- 收款与退款；
- 发票与发票明细行、发票明细行与应收；
- 摊销、折旧及其对应凭证；
- 一个审批申请下多个被审批单据的逐项执行状态。

### 8.3 属性和约束的取舍

原始实体定义中有大量数据库实现字段或派生字段，例如：

- `org_id`、`biz_line`、创建人和更新时间；
- 各类 `*_id` 外键；
- 已用金额、预占金额、已核销金额和未核销余额；
- 逾期天数、结清日、累计计提额和累计折旧额；
- 红冲标记和被红冲单据 ID。

当前模型的处理原则是：

1. 需要 LLM 理解和业务判断的稳定事实进入公共属性，例如 `amount`、`occurred_on`、`status`、
   `category`、`version`、`sequence` 和 `reason`。
2. 关系外键改为图关系，不把端点 ID 再存为普通业务属性。
3. 可由图和原始金额计算得到的余额和汇总不作为录入字段。
4. 尚未稳定、暂不值得提升为公共语义的结构先放入 `details`。

这意味着当前模型可以表达核心经营追溯和主要金额守恒，但并未覆盖原始模型的全部字段约束、
受控枚举、状态迁移和派生指标。

## 9. 覆盖结论和下一步

当前模型的更准确结论是：

| 判断维度 | 当前结论 |
| --- | --- |
| 核心经营主链 | 已覆盖客户、授信、方案、审批、合同、放款、计划、应收、收款、核销和结清 |
| 资金追溯 | 已用独立 `allocation` 表达收款到应收/罚息的金额分配，并有确定性守恒校验 |
| 业务执行 | 已有 13 个 Action；11 个 Action 通过 18 条前置条件形成偏序依赖，客户到结清可由 Action 形成完整状态闭环 |
| 原始概念覆盖 | 宽口径约 `24 / 35`，即 69%；独立 Object 类型为 `21 / 35`，即 60% |
| 完整性 | 仍缺贷后风险和催收、退款、合同附属计划、发票明细及资产会计等能力 |

> 当前模型已是一个可运行的融资租赁经营与资金追溯 MVP，但不是原始 35 实体数据模型的完整替代。

下一步应按实际业务目标增量扩展，而不是一次性搬入剩余 11 个实体：

1. 先完善审批流程模板、步骤主体和顺序校验，使已有审批闭环从“可执行”进入“受控”。
2. 若优先支持贷后经营，补充风险分类、催收和退款，并为它们定义 Action 和约束。
3. 若优先支持合同全量收支，补充保证金计划和费用计划，将其纳入应收、收款和核销主链。
4. 若优先支持精细核算，再补租金明细、发票明细、摊销和折旧。
