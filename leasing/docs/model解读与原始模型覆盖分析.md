# 融资租赁本体模型解读与覆盖分析

本文解释当前 `leasing/model.yaml` 的设计，并与 `融资租赁数据模型.puml` 及其包含的
`_实体定义.iuml` 做概念层面对照。

这里的“覆盖”不是把数据库字段逐个搬到 YAML，而是判断原始模型表达的业务概念，是否在当前
对象、关系、属性或 `details` 中仍然能够被表达和追溯。

## 1. 当前模型的基本想法

当前模型是一个面向融资租赁经营和资金追溯的对象关系模型。它只使用两种本体元素：

```text
Object    可独立识别、保存和追溯的业务事实
Relation  两个 Object 之间有方向、带业务语义的联系
```

模型没有按原始资料中的数据表和外键逐表复刻，而是保留对经营判断最重要的事实：

```text
客户 -> 授信 -> 项目方案 -> 合同 -> 放款
                                  |
                                  v
                         租金计划版本 -> 应收
                                              ^
                                              |
                         收款 -> 核销明细 ---+

合同 -> 变更版本 -> 结清
合同 -> 标的物、担保、审批、会计凭证
```

因此，模型主要回答四类问题：

- 这笔融资业务由谁参与、依据什么授信和方案形成？
- 合同产生了哪些放款、租金计划和应收？
- 到账资金核销了哪些应收或罚息，金额是否守恒？
- 合同发生了哪些审批、变更、结清和会计处理？

## 2. 当前对象类型

当前 `model.yaml` 定义 21 个对象类型。

### 主体和租前

| 对象 | 含义 |
| --- | --- |
| `party` | 出租方、资金方、业务部、风险部等经营主体。原始模型的 `lessor` 被概括为此类型。 |
| `customer` | 承租方、买方、卖方、保证人等客户侧主体。 |
| `credit` | 可使用的授信额度总量。 |
| `credit_entry` | 额度预占、正式占用、释放或冲销的一次变动流水。原始模型的 `credit_occupy` 被概括为此类型。 |
| `lease_plan` | 合同签订前的融资租赁项目方案。 |

额度不是直接修改余额，而是由 `credit_entry` 汇总得到预占和已用金额。这样可以保留额度变化
的原因、时间和来源。

### 合同和履约

| 对象 | 含义 |
| --- | --- |
| `contract` | 融资租赁核心合同，约定金额、期限、出租、承租和标的物责任。 |
| `contract_participation` | 合同参与方的事实，保存参与角色和生效信息。原始模型的 `contract_party` 被概括为此类型。 |
| `loan` | 合同项下实际投放资金的一次放款事实。 |
| `schedule_version` | 某一版租金计算和收款计划。原始模型的 `rent_version` 被概括为此类型。 |
| `change_order` | 展期、提前还款、利率调整、租金重排等合同变更事实。 |

租金计划采用版本方式管理。新计划通过 `supersedes` 替代旧计划，但不删除旧计划；已经生成的
应收和核销仍然保留原始来源。

### 应收和资金

| 对象 | 含义 |
| --- | --- |
| `receivable` | 一笔具体应收，可以是租金、费用或其他应收。 |
| `payment` | 一笔实际到账的资金。到账不等于已经核销。 |
| `allocation` | 收款分配给应收或罚息的独立事实，包含核销金额、日期和顺序。 |
| `penalty` | 应收逾期后计提的一笔罚息事实。 |
| `settlement` | 合同最终结算或部分提前结清事实。 |

`allocation` 是模型的关键设计：

```text
payment ->derives-> allocation ->references-> receivable
```

它可以表达一笔收款核销多笔应收，也可以表达一笔应收被多次收款分次核销。核销金额不能通过
普通无属性关系代替。

### 标的、担保和结果

| 对象 | 含义 |
| --- | --- |
| `subject_matter` | 租赁设备、车辆或受让应收账款等租赁标的及其价值事实。租赁物和受让应收账款的专属字段暂放在 `details`。 |
| `guarantee` | 保证人或担保物提供担保的金额、方式和顺位事实。 |
| `invoice` | 由应收或结算事实产生的开票结果。 |
| `voucher` | 业务事实投影形成的会计凭证头。 |
| `voucher_line` | 凭证下的借方或贷方分录。 |
| `approval` | 针对一个业务对象的一次审批决策事实。流程快照、审批历史和最终结果放在 `details` 中。 |

审批没有拆成流程、阶段、任务等多个对象。审批对象通过关系指向被审批对象和决策主体，关系
上的 `sequence` 表示顺序，相同顺序可以表达并行审批或会签。

## 3. 五种关系的语义

| 关系 | 当前含义 | 例子 |
| --- | --- | --- |
| `contains` | 一个对象包含组成或明细事实。 | `voucher -> voucher_line`、`contract -> contract_participation` |
| `references` | 一个事实引用另一个对象作为来源、依据或业务对象。 | `approval -> contract`、`allocation -> receivable` |
| `associates` | 两个独立对象存在业务联系，关系属性中的 `role` 说明具体联系。 | `payment -> customer`、`contract -> subject_matter` |
| `derives` | 一个业务事实经过业务处理产生另一个结果事实。 | `contract -> loan`、`schedule_version -> receivable` |
| `supersedes` | 新版本替代旧版本，旧事实保留。 | `schedule:v2 -> schedule:v1` |

原始 PUML 使用 UML 的包含、聚合和虚线关系表达 64 条具体连接；当前模型不为每一种连接
建立一个新的关系类型，而是用上述五个稳定关系加 `role` 表达具体业务含义。这是有意的
抽象，而不是遗漏了关系名称。

## 4. 业务主链示例

当前 seed 数据中的一笔示例业务可以读成：

```text
济南智造有限公司
    <-references- 智能产线融资租赁方案
    <-references- 综合授信额度
综合授信额度
    ->contains-> 额度预占流水
智能产线融资租赁方案
    ->derives-> 融资租赁合同
融资租赁合同
    ->contains-> 承租方/出租方参与事实
    ->derives-> 首笔放款
    ->derives-> 租金计划 V1
租金计划 V1
    ->derives-> 第 1 期租金、第 2 期租金
第 2 期租金
    ->derives-> 逾期罚息
客户
    <-associates- 收款 PAY-001
收款 PAY-001
    ->derives-> 核销明细
核销明细
    ->references-> 第 1 期租金 / 第 2 期租金
融资租赁合同
    ->derives-> 结清单
应收
    ->derives-> 发票
会计凭证
    ->contains-> 借方分录、贷方分录
审批申请
    ->references-> 融资租赁合同
审批申请
    ->associates-> 业务部、风险部、出租方
```

运行时还会检查三类金额不变量：核销不能超过收款或应收金额；额度流水汇总不能超过授信
额度；凭证借贷必须平衡。

## 5. 与原始 35 个实体的对照

`_实体定义.iuml` 定义了 35 个实体。当前模型定义了 21 个 Object 类型，但不是简单的
21 对 35 的删减：有些原始实体被改名为更通用的业务事实，有些被合并到一个对象的
`details`，另一些则确实尚未进入当前 MVP。

### 已覆盖或抽象覆盖的 24 个概念

| 原始实体 | 当前模型 | 处理方式 |
| --- | --- | --- |
| 客户 | `customer` | 直接覆盖 |
| 经营主体/出租方 | `party` | 用更通用的经营主体覆盖，不限定只能是出租方 |
| 授信额度 | `credit` | 直接覆盖 |
| 额度占用流水 | `credit_entry` | 统一表达预占、占用、释放和冲销 |
| 项目方案 | `lease_plan` | 改用更明确的领域名称 |
| 主合同 | `contract` | 直接覆盖 |
| 合同参与方 | `contract_participation` | 从外键关系提升为可追溯业务事实 |
| 放款 | `loan` | 直接覆盖 |
| 租金表版本 | `schedule_version` | 用“计划版本”表达版本演进 |
| 标的物主表 | `subject_matter` | 直接覆盖 |
| 标的物—租赁物 | `subject_matter.details` | 租赁物专属属性暂不独立建对象 |
| 标的物—受让应收账款 | `subject_matter.details` | 受让应收账款专属属性暂不独立建对象 |
| 担保关系 | `guarantee` | 直接覆盖 |
| 合同变更单 | `change_order` | 直接覆盖 |
| 应收计划明细 | `receivable` | 直接覆盖 |
| 逾期罚息计提 | `penalty` | 直接覆盖 |
| 收款单 | `payment` | 直接覆盖 |
| 核销明细 | `allocation` | 直接覆盖，并作为独立资金分配事实 |
| 结清单 | `settlement` | 直接覆盖 |
| 开票信息 | `invoice` | 直接覆盖 |
| 凭证 | `voucher` | 直接覆盖 |
| 凭证分录 | `voucher_line` | 直接覆盖 |
| 审批申请单 | `approval` | 直接覆盖，但内部流程信息收进 `details` |
| 审批单据明细 | `approval.details.history` 与关系 | 不单独建对象，折叠为审批历史和参与主体关系 |

因此，按“概念是否还能表达”统计，当前模型覆盖约 `24 / 35` 个原始实体概念，约 69%。
按 YAML 中独立 Object 类型数量统计则是 `21 / 35`，约 60%；差异来自上表中的合并和抽象。

### 尚未作为独立对象覆盖的 11 个概念

| 原始实体 | 当前状态 | 影响 |
| --- | --- | --- |
| 从合同 `sub_contract` | 未建模 | 无法独立追踪主合同下的从合同及其金额、类型和来源 |
| 保证金计划 `deposit_plan` | 未建模 | 方案、合同或放款约定的保证金计划无法结构化追踪 |
| 费用计划 `fee_plan` | 未建模 | 手续费等费用的计划、内扣和税率无法独立追踪 |
| 租金表明细 `rent_line` | 未建模 | 租金版本没有单独的本金、利息、计息区间明细；目前直接生成 `receivable` |
| 担保物 `collateral` | 未建模 | 无法独立表达担保物评估价值、权证和状态 |
| 风险分类记录 `risk_class` | 未建模 | 无法保存五级分类、IFRS9 阶段和减值准备的历史记录 |
| 催收记录 `collection` | 未建模 | 无法保存催收方式、结果、承诺还款日和后续跟进 |
| 退款单 `refund` | 未建模 | 收款退款及其对应资金回退链尚不能表达 |
| 发票明细行 `invoice_line` | 未建模 | 发票只能记录总额，不能将多个应收拆到发票行 |
| 摊销区间 `amortization` | 未建模 | 不能表达按期间计算的本金、利息及未实现融资收益 |
| 资产折旧 `depreciation` | 未建模 | 不能表达租赁标的的折旧方法、累计折旧和账面净值 |

这些概念不是都必须马上补齐。对于 MVP，`rent_line`、`invoice_line` 等明细可以先由
`details` 或应收对象承载；但风险分类、催收、退款、摊销和折旧如果是实际经营分析的重点，
后续应优先提升为独立对象，因为它们具有独立生命周期和历史追溯需求。

## 6. 关系覆盖情况

### 已能直接或间接表达的关系

以下原始关系已经被当前五种关系覆盖：

- 客户获得授信、客户申报方案：通过 `references` 表达。
- 授信产生额度流水：通过 `contains` 表达。
- 方案落地为合同：通过 `derives` 表达。
- 合同参与方：通过 `contains` + `contract_participation -> references -> party/customer` 表达。
- 合同产生放款、租金计划、应收、罚息、结清：通过 `derives` 表达。
- 收款与付款人、合同与标的物/担保、担保与保证人：通过 `associates` 表达。
- 收款与核销、核销与应收/罚息：通过 `derives` + `references` 表达。
- 凭证与分录：通过 `contains` 表达。
- 审批与被审批对象、审批参与主体：通过 `references` + `associates` 表达。

部分原始模型中的直接外键，在当前模型中被改成了业务路径。例如原始模型有“合同直接指向
客户”和“应收直接指向合同、放款、租金版本”，当前更关注来源事实：应收由租金计划派生，
租金计划又由合同派生，因此可以沿图追溯到合同，而不重复保存多个平行外键关系。

### 当前确实缺少的关系能力

由于对应对象尚未建立，以下关系目前也不能独立表达：

- 合同与从合同、从合同与标的物来源合同；
- 方案/合同/放款与保证金计划、费用计划；
- 租金版本与租金明细；
- 标的物与担保物、担保物与担保关系；
- 合同与风险分类、催收记录；
- 收款与退款；
- 发票与发票明细行、发票明细行与应收；
- 摊销、折旧及其对应会计凭证；
- 一个审批申请与多条审批单据明细之间的独立对象关系。

当前 `relation_types` 只有 5 种，这是有意的语义收敛。原始 PUML 的 64 条关系线并不意味着
需要 64 种关系类型；真正需要补齐的是上面这些业务事实和端点，而不是继续增加诸如
`contract_to_loan`、`payment_to_receivable` 这样的关系名称。

## 7. 属性和业务约束的差异

原始实体定义中大量字段属于数据库实现字段或派生字段，例如：

- `org_id`、`biz_line`、创建人和更新时间；
- 各类 `*_id` 外键；
- 已用金额、预占金额、已核销金额、未核销余额；
- 逾期天数、结清日、累计计提额、累计折旧额；
- 红冲标记和被红冲单据 ID。

当前模型的处理原则是：

1. 稳定且需要 LLM 判断的字段进入公共属性，如 `amount`、`occurred_on`、`status`、`category`、
   `version`、`sequence` 和 `reason`。
2. 关系外键改为图关系，不再把 `客户id`、`合同id`、`来源单据id` 重复保存为普通属性。
3. 可由图计算得到的余额和汇总不作为录入字段，而由确定性函数计算。
4. 尚未稳定、暂不值得成为公共语义的字段放入 `details`。

因此，当前模型已经表达了主要业务守恒约束，但还没有覆盖原始模型全部的字段级约束和派生指标。

## 8. 结论：还差多少

如果目标是“用 LLM 理解融资租赁主链并完成 MVP 操作”，当前模型已经覆盖核心路径：

```text
客户 / 授信 / 方案 / 合同 / 放款 / 租金计划 / 应收 /
收款 / 核销 / 罚息 / 变更 / 担保 / 结清 / 发票 / 凭证 / 审批
```

如果目标是“覆盖原始 PUML 的完整业务数据模型”，还缺 11 个独立对象及其关系：

```text
从合同、保证金计划、费用计划、租金表明细、担保物、风险分类、
催收记录、退款单、发票明细行、摊销区间、资产折旧
```

所以更准确的判断是：

> 当前模型已覆盖原始模型的核心经营主链和资金追溯主链，概念覆盖约 69%；
> 但在贷后管理、合同附属计划、发票明细和资产会计方面仍有明显缺口，暂不能称为完整模型。

下一步不应一次性把 11 个对象全部加入。建议按业务优先级逐步补齐：先补退款、风险分类、催收
和保证金/费用计划，再根据实际核算需求补租金明细、发票明细、摊销和折旧。
