# 高速联网收费领域本体模型 V3.1 问题分析

## 1. 总体判断

《高速联网收费领域本体模型 V3.1》覆盖了联网收费业务的大部分资料，包括 138 个实体、约 200 条具体关系以及大量字段和枚举，适合作为领域资料目录和数据字典使用。但它还不是一个边界清晰、语义一致、可以直接用于业务图和 LLM 推理的本体模型。

文档当前最主要的问题不是实体数量不足，而是同时混合了业务概念、数据库记录、配置文件、设备台账和计算结果。部分对象重复表达同一业务身份，部分 ID 字段实际代表关系，关系方向和生命周期也存在不一致。若直接照搬，会得到一个类型很多、重复边很多，但业务事实仍难以追溯的图。

## 2. 主要问题

### 2.1 模型层次混在一起

文档没有明确区分以下层次：

- 稳定的领域概念，例如车辆、通行、收费站和账户。
- 业务记录，例如入口交易、充值交易、查验结果和清分结果。
- 计算或配置产物，例如费率文件、最小费额路径和计费动态库。
- 物理设备台账，例如栏杆机、补光灯、服务器和密码卡。
- 来源数据库字段，例如 `operType`、`lastVer`、文件路径和组合字符串。

这些内容全部被放在同一级“实体”下，使模型更像多个业务系统表结构的汇总。对 LLM 而言，138 个并列类型会掩盖真正重要的业务主链。

### 2.2 类型粒度不一致

同一模型内采用了不同的拆分标准：

- 收费公路业主、发行机构、省中心、部中心和操作员分别建成类型，但它们本质上都是承担不同角色的业务主体。
- 35 种硬件设备分别建成类型，但生命周期和关系模式大体相同。
- 11 种名单和 18 种运行参数也分别建成类型，差异主要是类别和参数内容。
- 入口、出口和门架交易分别建模，但三者共享交易流水、车辆识别、计费和位置等主要语义。
- 用户、车辆、ETC 卡和 OBU 的客服操作分别建成业务记录，实际都属于“针对某个业务对象办理一次客服业务”。

结果是：有些业务差异通过类型表达，有些通过字段表达，没有统一的判断原则。

### 2.3 将对象标识当成普通属性

文档中大量 `passId`、`vehicleId`、`obuId`、`cardId`、`stationId`、`laneId`、`gantryId` 和 `tollIntervalId` 实际都在说明对象之间的联系，却被重复定义为字符串属性。

例如入口交易同时保存 `passId`、`vehicleId`、`obuId`、`stationId` 和 `laneId`。如果这些对象已经存在于图中，这些 ID 应优先成为关系，而不是再复制一组字符串。否则会出现两个无法自动保证一致的数据来源：

```text
EntryTransaction.passId = P001
Passage(P001) -> references -> EntryTransaction
```

一旦字段和图边不一致，模型没有说明以哪一个为准。

### 2.4 同一关系被重复表达

文档常同时使用属性、对象属性和反向关系表达同一事实。例如：

- `Passage` 引用入口交易，而入口交易又保存 `passId`。
- `TollPlaza contains TollLane`，同时又定义 `TollLane references TollPlaza`。
- 车辆在 2.1.1 中 `references OBU/ETCCard`，在 2.1.7 中又由 `OBU/ETCCard associates Vehicle` 反向表达。
- 牌识记录既作为交易对象属性出现，又由 `Passage` 直接引用。

这些捷径边会增加写入和维护成本。只要某项联系可以沿已有路径唯一推导，就不应默认重复保存；只有查询性能、来源证据或历史快照确实要求时，才应显式冗余并声明同步规则。

### 2.5 临时业务事实被建成长周期关系

文档将 `CPCCard associates Vehicle` 和 `PaperTicket associates Vehicle` 定义为 N:N 关系，但没有表达关系发生在哪一次通行中。

CPC 卡和纸券是在入口临时发放、出口回收或出示的介质。同一张 CPC 卡会先后服务多辆车。如果只保存卡与车辆的 N:N 关系，无法回答：

- 某辆车的哪次通行使用了这张卡？
- 卡在何时、哪个入口被发放？
- 卡是否在对应出口被回收？

这类联系必须通过通行及入口/出口交易表达，而不是直接建立无时间上下文的车卡长期关系。

### 2.6 `derives` 的方向不一致

文档对 `derives` 没有贯彻统一方向。费率域通常使用“来源 -> 结果”，例如：

```text
BaseRate -> derives -> ProvincialRate
```

但客服资金域存在大量反向定义：

- `Bill derives ETCConsumptionDetail`，文字却说账单由消费明细汇总产生。
- `BillSettlementResult derives Bill`，实际应是账单产生结算结果。
- `UserAccountDetail derives RechargeTransaction`，实际应是充值交易产生记账明细。
- `BusinessDayEndSummary derives RechargeTransaction`，实际应是交易汇总为日结。
- `ReconciliationResult derives ...`，实际应是被核对的业务事实产生对账结果。

如果派生方向不稳定，图遍历无法可靠区分“向前追结果”和“向后找依据”。建议统一为：

```text
来源事实 -> derives -> 计算、汇总或处理结果
```

### 2.7 一些“实体”本质上是关系

以下对象主要由两个或多个端点 ID 构成，其业务本质更接近关系：

- `NodeRelation`：路网节点之间的可达或相邻关系。
- `ReplaceRelation`：门架与被代收费单元之间的关系。
- `ProvinceBoundaryRelation`：本省与外省边界设施之间的关系。
- `UnderRelationParameter`：收费站承载门架的关系配置。

其中 `RoadNode` 还会与已有收费站、收费单元或门架重复表达节点身份。直接照搬后，需要长期同步“设施对象”和“路网节点对象”。更自然的做法是复用已有设施作为节点，用有方向的图边表达拓扑；只有关系本身拥有独立审批、版本或生命周期时，才将它提升为对象。

### 2.8 独立对象和发布包成员混淆

文档定义 `FeeModule contains TollGantry`，理由是计费模块包含门架字典。但收费门架是独立存在的物理设施，不依附于某个计费模块存在。真正属于模块的是某一版本的门架配置或门架快照，而不是门架本身。

这种场景更适合：

```text
FeeModule -> contains -> 版本化配置项
版本化配置项 -> references -> TollGantry
```

MVP 中也可以简化为计费规则直接引用门架，但不应把物理设施视为发布包的组成部分。

### 2.9 主数据、观察值和历史快照没有区分

车牌、车型、车种和介质信息在车辆档案、入口交易、门架交易、牌识记录、查验结果、二次计费和发票数据中反复出现。这里既有冗余，也有必须保留的历史事实：

- 车辆档案中的车型是当前主数据。
- 牌识记录中的车牌是当时设备观察值。
- 交易中的车型是当时实际采用的计费车型。
- 发票基础数据中的字段可能是开票时冻结的业务快照。

文档没有说明哪些字段应通过关系取得，哪些必须作为不可变快照保留。简单删除重复字段会丢失历史事实，全部保留又会制造冲突。模型应为每个重复字段说明它属于“主数据、观察值还是业务快照”。

### 2.10 使用组合字符串模拟集合和关系

文档中存在大量用字符串保存集合或明细的字段，例如：

- `RoadNode.gantrys`
- `ReplaceRelation.tollIntervals`
- `GantryTransaction.tollIntervalId/payFeeGroup/feeGroup`
- `TransactionSplitBasisRecord.splitBasisGantryGroup`
- `InvoiceBasisData.sectionId/tollIntervalId/tollIntervalFee`
- 以 `|` 分隔的车型、车牌或参数集合

这些字段适合文件交换，却不适合作为领域图的主要表达。它们无法直接校验端点是否存在，也不便查询单个收费单元的费用。集合成员和金额明细应优先表达为对象或关系；原始组合字符串可以作为来源快照保留在 `details` 中。

### 2.11 客户、车主和账户边界含糊

文档同时存在 `VehicleOwner`、`User`、`UserAccount` 和 `CardAccount`：

- `User` 有时称“客户账户 / 用户”，容易与资金账户混淆。
- `VehicleOwner` 与 ETC 开户客户可能是同一主体，也可能不同，但没有统一主体模型承载这种角色关系。
- `ETCCard associates User` 的说明又称“关联用户账户”，混淆客户身份和资金账户。

建议明确区分：业务参与者、开户客户、车辆权属关系和资金账户。相同现实主体可以承担多个角色，但不应因角色不同重复创建互不关联的身份对象。

### 2.12 资金业务缺少统一记账视角

文档列出了充值、圈存、冲正、退费、退款、补交、缴费、消费、用户账户明细和卡账户明细，但没有形成统一的资金变化模型：

- 交易与实际账户记账结果之间的方向不统一。
- 原交易、调整交易和冲正交易的来源关系主要依赖 ID 字段。
- 账户余额、交易金额和记账后余额之间缺少一致性约束。
- 账单缴费、账单结算与账户记账之间的边界不清楚。

因此文档可以列出资金记录，却较难回答“一笔充值最终进入了哪个账户”“一笔冲正抵消了哪次记账”等追溯问题。应把资金交易视为来源事实，把账户记账明细视为余额变化结果，并用关系连接原交易、调整交易、账户和账单。

### 2.13 业务结果与业务行为分离

文档主要描述静态实体及其关系，没有定义建立或改变关系的业务行为。例如：

- 车辆与 OBU 的绑定由什么行为建立、何时解除？
- CPC 卡的发放和回收如何保证属于同一次通行？
- 预追缴记录经过什么行为转为正式追缴？
- 费率规则如何发布、生效和失效？
- 充值、记账和冲正需要同时满足哪些写入约束？

没有 Action 或状态迁移规则，前端只能退化为通用“新增对象/新增关系”，Agent 也无法从用户意图推导出完整且一致的业务变更。

### 2.14 约束大多停留在说明文字

文档虽然给出了基数，但缺少可执行的约束定义，例如：

- 哪些属性必填、唯一或不可变。
- 关系允许连接哪些对象类型。
- 同一时间是否只能存在一条有效绑定。
- `derives` 是否允许形成环。
- 时间区间是否允许重叠。
- 金额、币种和计量单位如何统一。
- 删除或失效对象时如何处理关联记录。

此外，`Date`、`DateTime`、`Decimal`、`Long` 的使用和金额单位并不完全一致，版本、复核状态和 `operType` 等来源系统字段也被大量重复。它们需要在数据契约层统一，而不是散落在每个实体说明中。

## 3. 几个典型冲突

| 场景 | 文档当前表达 | 问题 | 建议表达 |
| --- | --- | --- | --- |
| 车辆与 OBU | `Vehicle references OBU`，另有 `OBU associates Vehicle` | 同一事实双向重复，关系类型还不同 | 保留一条带 `bound_obu` 角色和有效期的关系 |
| 车辆与 CPC 卡 | `CPCCard associates Vehicle` N:N | 缺少具体通行和发放回收时间 | `Passage -> used_cpc_card`，入口/出口交易记录发放和回收 |
| 交易位置 | 交易同时保存站 ID、车道 ID，并定义设施关系 | 收费站可从车道归属推导 | 交易只关联实际车道，沿车道归属取得收费站 |
| 牌识记录 | 交易内嵌牌识对象，通行又直接引用牌识记录 | 来源和归属重复 | 交易关联牌识记录，通行通过交易取得牌识事实 |
| 账户记账 | `AccountDetail derives Transaction` | 派生方向颠倒 | `Transaction -> derives -> AccountEntry` |
| 账单汇总 | `Bill derives ConsumptionDetail` | 派生方向颠倒 | `ConsumptionDetail -> derives -> Bill` |
| 路网拓扑 | `RoadNode` + `NodeRelation` + 端点 ID | 与收费站/门架重复建点，边又对象化 | 设施对象之间建立有向 `route_next` 边 |
| 计费模块 | `FeeModule contains TollGantry` | 物理门架不依附于参数包 | 模块内配置项引用门架，或规则直接引用门架 |
| 费额组合 | 多个收费单元和金额放入组合字符串 | 无法逐项关联、查询和校验 | 每个收费单元建立一条带金额的明细关系 |

## 4. 当前 OMS 模型已经采用的处理方式

当前 `oms/model.yaml` 没有逐表复制 V3.1，而是做了以下收敛：

- 本体层只保留 `Object` 和 `Relation`，业务类型位于语义模型。
- 多类组织和人员统一为 `party`，用 `category` 表达业务角色；开户客户保留为 `user`。
- 35 种设备统一为 `business_device`，服务区、网点和线上渠道等统一为 `service_facility`。
- 入口、门架和出口交易统一为 `toll_transaction`，用 `stage` 区分阶段。
- 多类客服业务统一为 `customer_service_record`。
- 多类资金交易统一为 `account_transaction`，用户和卡账户明细统一为 `account_entry`。
- 多类费率、优惠、代收和路径记录统一为 `fee_rule`。
- 11 种业务名单统一为 `control_record`，18 种运行参数统一为 `operating_parameter`。
- `RoadNode` 不重复建模，收费站和门架直接作为节点，使用 `route_next` 表达拓扑。
- ID 型外键优先转换为关系；可沿图唯一推导的捷径关系不重复保存。
- CPC 卡和纸券通过具体通行及入口、出口交易表达临时使用事实。
- `derives` 统一为“来源事实 -> 结果对象”。
- Action 描述业务行为如何产生一组对象和关系变更，前端与 Agent 共用同一语义。

## 5. 当前 OMS 仍需继续完善的部分

上述抽象解决了模型规模和关系重复问题，但还没有完全解决 V3.1 的所有业务知识：

- `category` 目前是开放字符串，设备、名单、费率、客服业务和运行参数的推荐词汇尚未系统定义。
- 充值、圈存、冲正、退费、退款、补交和账单缴费之间的来源关系还缺少完整 Action。
- 设备内部组成关系只具备通用表达能力，RSU、PSAM 卡等关键结构还没有明确业务操作。
- 运行参数之间的依赖关系和适用范围尚未形成稳定规则。
- 业务日结已有对象类型，但尚无对应的生成操作。
- 唯一性、有效期重叠、绑定互斥、金额守恒等跨对象约束尚未实现。
- 历史快照与主数据的保留原则还需要在接入真实数据源时逐字段确认。

## 6. 后续建模原则

后续不应以提高“138 个实体的一对一覆盖率”为目标，而应按以下标准判断是否需要新增类型或关系：

1. 对象是否有独立业务身份和生命周期。
2. 对象是否需要被单独查询、授权、追溯或关联。
3. 差异是否只是类别和属性，能否用现有类型加 `category` 表达。
4. ID 字段是否实际指向另一个对象，能否转换为关系。
5. 关系是否已经可以沿现有图路径唯一推导。
6. 临时联系是否绑定到了产生它的业务过程和时间。
7. 派生关系能否稳定回答“结果来自什么”和“来源产生了什么”。
8. LLM 是否需要理解该细节，还是只需在 `details` 中保留来源数据。

以这些原则衡量，V3.1 应作为领域知识来源和数据字典，而不是直接作为最终运行时本体。运行时模型应保留其业务主干、关键事实和追溯关系，同时主动消除表结构、重复外键和实现细节带来的复杂度。
